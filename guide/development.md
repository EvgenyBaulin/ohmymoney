# Для разработчика

## Сборка из исходников

Нужны macOS 26 или новее с **Xcode 27** и [XcodeGen](https://github.com/yonaskolb/XcodeGen)
(`brew install xcodegen` или `scripts/install-xcodegen.sh <dir>`, если нужна ровно та версия,
что на CI). Проект Xcode генерируется из `project.yml` и в git не хранится.

```sh
make              # сгенерировать проект, собрать Debug, запустить
make test-core    # тесты ядра на чистом Swift — быстрый цикл
make test         # тесты приложения
make verify       # формат, lint, все тесты, обе сборки, а также проверки, которые запускает CI
make sample       # приложение на синтетических данных за полгода, в отдельной папке
make sample-large # то же на примерно 20 000 операций за два года
make demo         # демо-база за год из нового случайного seed, в отдельной папке
make demo SEED=<n>  # та же демо-база ещё раз — в тот же день и на том же языке интерфейса
make migration-dry-run DB=<finance.sqlite>  # обновление схемы на копии базы: только счётчики
make pyenv        # venv с pandas, чтобы тесты CSV действительно перечитывали выгруженные таблицы
```

`make demo` открывает сборку Debug на наборе данных `demo` — в заголовке окна «DEBUG · DEMO»:
двенадцать месяцев операций, счета в нескольких валютах и группа вне сводки, переводы с
комиссией в рублях и в долларах, обмен валют, сверки, старая карта, объединённая с основной и
лежащая в архиве, возвраты покупок и частичный возврат денег, разовая трата, цель в долларах,
бюджеты событий. Есть в ней и новое 1.2: карты (у основного счёта — ещё и виртуальная) с
правилами кэшбэка «всегда» и «только в месяце», покупка с вписанным кэшбэком, отель в бюджете
новогоднего события, цель, внесённая вперёд по плану, ожидаемая зарплата на счёт, место в
архиве, однодневное событие, кредитная карта в минусе, перевод с точным временем и поздняя
сверка, разница которой следует за операцией, внесённой после неё, — и один просроченный
плановый платёж. Каждый запуск берёт новый случайный seed и печатает команду, которая соберёт ту
же базу снова: история кончается сегодняшним днём, а названия в ней — на языке интерфейса, так
что `make demo SEED=<n>` повторяет базу в тот же день и на том же языке. Seed записан и в журнал
набора. Наборы данных лежат в своих папках и никогда не трогают базу Debug.

Сборка Debug — отдельное приложение: её bundle id — `io.github.EvgenyBaulin.ohmymoney.debug`, у неё
свои контейнер, настройки и бэкапы, красная полоса «DEBUG» на значке и «DEBUG» в заголовке окна.
Копию в /Applications она никогда не трогает. Продукты сборки лежат вне репозитория, в
`~/Library/Developer/OhMyMoney/`; `Build.nosync` — ссылка туда.

Необязательно: `scripts/make-signing-identity.sh` создаёт самоподписанный сертификат
«OhMyMoney Local Signing» в вашей связке ключей «вход». С ним сборки Debug сохраняют одну и ту же
подпись от сборки к сборке, поэтому разрешения, которые macOS даёт UI-тестам, переживают
пересборку; без него всё подписывается ad hoc. `make hooks` подключает к git хуки репозитория.

## Структура

| Путь | Что внутри |
| ---- | ---------- |
| `Schema/` | SQL-миграции, общие для всех платформ; они идут только вперёд |
| `Packages/AppCore/` | вычислительное ядро: деньги, выражения, разбор строки ввода, курсы, учёт, аналитика, планирование, модель категорий, формат архива, синтетические данные. Чистый Swift и Foundation; собирается и тестируется на Linux |
| `Packages/AppDatabase/` | слой хранения на GRDB: миграции, записи, репозитории; `ohmymoney-migration-dry-run` — пробное обновление копии базы (`make migration-dry-run`) |
| `Apps/macOS/App/` | точка входа, сцены, меню и параметры запуска |
| `Apps/macOS/Features/` | ввод, операции, обзор, аналитика, отчёты, планирование, сверка, долги, счета, настройка счетов при первом запуске, настройки |
| `Apps/macOS/Platform/` | база данных, бэкапы, экспорт, архив, курсы, обновления, конвейер расчётов, журнал |
| `Apps/macOS/Shared/` | дизайн-система, локализация, графики |
| `Apps/macOS/Resources/` | Info.plist, entitlements, String Catalogs, значки |
| `Apps/macOS/Tests/`, `Apps/macOS/UITests/` | тесты приложения и UI-тесты |
| `scripts/` | проверки `make verify`, скрипты выпуска, хуки git |

## Выпуск

Для сопровождающего; каждый шаг выполняется на его Mac.

1. В `project.yml` увеличьте `CURRENT_PROJECT_VERSION` — **Sparkle сравнивает именно это
   число**, а не короткую версию — и задайте `MARKETING_VERSION`. Добавьте в `CHANGELOG.md`
   раздел `## [X.Y.Z] — <date>`.
2. `make release` делает остальное одной командой и ничего не спрашивает: проверяет ветку,
   что тега этой версии ещё нет и что номер сборки вырос; прогоняет `make verify`; коммитит
   рабочее дерево; собирает Release с публичным ключом из `sparkle-public-key.txt`, проверяет
   bundle id, ключ, версию и подпись внутри собранного, упаковывает `OhMyMoney-X.Y.Z.zip` и
   подписывает его приватным ключом из связки ключей «вход» утилитой Sparkle `sign_update`
   (`make release-local`); отправляет `main` и ждёт зелёного CI на этом коммите; создаёт выпуск
   `vX.Y.Z` на GitHub с разделом CHANGELOG в описании; добавляет запись в `appcast.xml` на ветке
   `gh-pages` новым коммитом и проверяет опубликованную ленту (`make release-check`). Любая
   ошибка до выпуска останавливает команду, и ничего не публикуется; `--force` и правки истории
   она не делает. `make release ARGS=--dry-run` печатает проверки и план и ничего не меняет.

Приватный ключ EdDSA никогда не попадает в репозиторий; потеряете его — и установленные копии
уже никогда не получат обновлений, поэтому держите его копию в менеджере паролей.
`.github/workflows/release.yml` — выпуск на GitHub Actions, без Mac сопровождающего. Он
собирает Release той же командой `make release-local`, подписывает его тем же сертификатом
«OhMyMoney Local Signing», проверяет сборку так, как её встретит установленная копия (в том числе
что она удовлетворяет designated requirement последнего выпуска), создаёт выпуск `vX.Y.Z`,
добавляет запись в `appcast.xml` на `gh-pages` и читает опубликованное обратно
(`make release-check`). Запускается кнопкой «Run workflow» на вкладке Actions или
`gh workflow run release.yml -f version=X.Y.Z` (на `main`), а также отправленным тегом
`vX.Y.Z`, у которого ещё нет выпуска.

- ему нужны четыре секрета репозитория: `SPARKLE_PRIVATE_KEY` (приватный ключ в том виде, в
  каком его записывает `generate_keys -x`), `SPARKLE_PUBLIC_KEY`, `OHMYMONEY_SIGNING_P12_BASE64`
  (сертификат подписи с ключом, выгруженный в `.p12` и закодированный в base64) и
  `OHMYMONEY_SIGNING_P12_PASSWORD` (пароль этого `.p12`);
- пока хотя бы одного секрета нет, workflow ничего не собирает и не публикует: первое задание
  называет недостающие в предупреждении и завершается;
- ключи живут только во время подписи — во временной связке ключей и временном файле раннера,
  которые удаляются до публикации;
- если выпуск уже опубликован вручную, workflow останавливается на первом задании.
